# Day 8 Reflection

The most difficult concept in this course was designing for concurrent requests without allowing data to become inconsistent. In a ticketing system, two buyers can see the same seat as available and try to reserve it at almost the same time. I worked through this by distinguishing the seat map's displayed availability from the authoritative hold operation. A database transaction, row locking, a unique constraint on each seat claim, and idempotency keys work together to prevent duplicate bookings and charges.

The feedback on my capstone showed me that a design must be complete when it is delivered, not merely strong in its opening sections. My requirements and traffic estimates were useful, but the submitted document stopped after the API section, leaving out the data model, concurrency controls, architecture, and trade-offs. I would improve my submission process by checking every required section against the assignment rubric, reviewing the complete file after saving it, and confirming that the correct version was committed and pushed. I would also replace generic reflection text with specific lessons from the feedback.

Next, I want to learn practical load testing and observability. I plan to practise measuring response times, throughput, database contention, and failure rates under simulated traffic. I also want to build a small example of transactional seat holds and idempotent payment handling so I can test how the design behaves when requests arrive simultaneously or a payment response is delayed.
